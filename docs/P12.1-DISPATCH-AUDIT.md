# P12.1 — the routed-overflow validity mask: audit and correction

Status: **audit complete, defect confirmed, correction implemented behind a
default-off flag.** The registered T2 comparison is **not** changed: every arm
continues to run the placement it was trained and evaluated with. This document
is the audit note the plan asks for (`docs/PROGRAM-PLAN.md` P12.1); the receipt
it quotes is `results/t2/dispatch-audit-20261115T234953Z.json`, revision
`f13581f58a872b4a7315410f9e83f0ec3df49b74`, and the tests are
`oracle/tests/test_p12_1_dispatch.py` against
`oracle/train/reference_dispatch.py`.

## 1. The question

`oracle/train/modeling._RoutedDispatch` implements capacity dispatch. For a
forward pass over `T` positions with `k` selections per position and `m` experts:

1. the `T*k` pairs are built **token-major** (`pair = token*k + slot` where
   `slot` is the router's ranking order);
2. they are sorted by expert id with a stable sort, giving the **sorted order**;
3. each pair's **slot within its expert** is its index in that expert's block,
   and it is kept iff that index is below
   `capacity = max(1, ceil(T*k/m*factor))`, `factor = 1.25`;
4. the kept pairs are evaluated in a `[m, capacity, hidden]` buffer and the
   results are returned to the token and summed over the `k` slots.

The audit's question is narrow: **is the overflow mask applied to the pairs it
describes?**

## 2. The finding

No. `dispatch` returns `valid` indexed by **sorted position**. `combine`
restores the pair outputs to **token-major** order and then multiplies by
`valid`:

```python
flat_out = output.reshape(-1, hidden).index_select(0, row)   # sorted order
flat_out = flat_out.index_select(0, inverse)                 # token-major order
flat_out = flat_out * pair_weight.unsqueeze(-1)              # token-major: right
flat_out = flat_out * valid.unsqueeze(-1)                    # sorted: WRONG pair
```

So token-major pair `p` is gated by the validity of the pair whose *sorted
position* is `p`. That is a different pair whenever the sort permutation is not
the identity, i.e. whenever **any** expert overflowed. Two consequences, both
real:

* a pair that was executed in the buffer has its contribution **silently
  dropped**;
* a pair that overflowed is **retained** and reads its **clamped** buffer row,
  `m*capacity - 1`, which belongs to a different pair — when the overflowing
  expert is the last one, that row holds **another token's** activation, scored
  with that expert.

The module docstring claimed the opposite ("overflow pairs are dropped and
counted"; "their contribution is masked out later"). The dispatch half is
correct — a dropped pair is never copied into the buffer — which is why the
defect is invisible in the buffer: it lives entirely in the gating order.

## 3. Reproduction

`oracle/train/reference_dispatch.py` is an independent transcription written
from the specification (explicit loops over pairs, explicit buffer rows, no
`index_copy_`, no scatter, no reshape-and-reduce). It models both placements:

* `mask_mode="pair"` — the documented semantics;
* `mask_mode="sorted"` — the shipped behaviour, gating token-major pair `p` by
  sorted position `p`.

`oracle/eval/dispatch_audit.py` checks, on a case matrix (no overflow, one
overflowing expert, an overflowing last expert, ties, duplicate expert ids,
`k = 1`, `k = m`, a single token, zero tokens, `k = 0`, and capacity factors

  test) — `dispatch_halves_bitwise_equal`;

  generation prefills. The evaluation receipts written **before this audit**
  record no dropped-pair count, so the evaluation-time exposure of the finished
  arms is unknown rather than small. Evaluation now records it
  (`baseline.py` → `dispatch`), and training records a run total
  (`summary.json` → `dispatch`).
* **The utility labels are unaffected.** `H*`'s leave-one-expert-out passes run
  with `full_bank=True`, which bypasses the router and the capacity dispatch
  entirely. P12.2's inputs are therefore untouched by this defect.
* **Step-0 parity is unaffected.** Every `W_down` is zero at step 0, so the
  bank's contribution is exactly zero whatever the gating order does.

## 7. The correction

`_RoutedDispatch` gained two attributes, both defaulting to the shipped
behaviour:

* `capacity_factor` (default `1.25`) — the registered value; exposed so a test
  can reach overflow deterministically instead of monkeypatching a module
  constant;
* `mask_order` ∈ `{"legacy", "pair"}` (default `"legacy"`) — `"pair"` applies
  the weight and the mask **before** the restore, to the pair each tensor slot
  actually holds, then restores.

`ArmModel.set_mask_order`, `build_arm(..., mask_order=...)`, `loop.py
--mask-order` and `baseline.py --mask-order` expose it. The placement is written
into `run-meta.json`, `summary.json` and every evaluation receipt
(`instrument.dispatch_mask_order`), so no consumer has to guess. A run that does
not pass the flag records `legacy` and is byte-identical to the registered arms.

**Amendments for receipts that predate the field (2026-11-16, S20).** Arms
`X` and `H` trained before this field existed, so their `run.json` cannot state
their placement. `results/t2/PROVENANCE-AMENDMENT-X-and-H.json` certifies it from
repository history and a fixed-batch replay (`legacy`), and the capability
adapter consumes it only under `--provenance-amendment`
(`docs/CAPABILITY-COURT.md`). The original receipts are unedited; the amendment
is a separate, hash-bound record.

**Not affected:** `D` (dense adapter) and `M` (hashed memory) — neither contains
a `_RoutedDispatch`. `D0` is the unmodified core. T1's `A`/`A0`/`B` share the
class, so any future T1 run inherits the same exposure; T1's recorded smoke
receipts already predate the slot-wise combine and claim no measurement.

**What is not done and must not be done silently:** the registered T2 arms and
thresholds are untouched. Re-training an arm with the corrected placement would
be a different arm, so it becomes a separate, labelled comparison.

**The cheapest decisive follow-up (evaluation only, no retraining):** evaluate
the trained `X` checkpoint under the corrected placement and compare its
receipt to `results/eval/t2-X.json`:

```bash

    --profile t2 --arm X --model-size 0.6b \
```

**The sensitivity re-run (training)**, only after the registered verdict is
published: the T2.8 replication tier (`H*`, `H`, `X` at one quarter of the
budget, three seeds) is the cheapest way to measure whether the defect moved the
decisive comparison; run it with `--mask-order pair` and report it as `V2`, never
as a replacement for the registered numbers. Until then the honest reading of
the pilot is: *produced by a dispatcher whose overflow mask is applied to the
wrong pairs, at a measured overflow rate of about one percent of pairs and up to
a quarter of a layer's pairs at a sampled step.*
